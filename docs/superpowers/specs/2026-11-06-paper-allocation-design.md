# Recover Paper allocation into the execution workflow

## Intent and chosen approach

Recover the useful implementation from the five unfinished October 29 files into this repository. The owner selected a generic Paper order runner integrated with the existing order lifecycle, rather than an offline-only calculator. Copying the old runner unchanged would retain expired authorization, fixed USMV prices and a parallel execution path; an offline-only migration would not meet the selected scope.

The recovered files remain intact until integration, provenance and retention checks are complete. Their old date, 55% allocation, account assumptions and reference close do not authorize any new order.

## Scope and constraints

Implement a reusable cash-backed allocation policy, a guarded one-attempt Paper workflow, an IBKR limit-order adapter, replayable audit events, a read-only reconciliation command and English/zh-CN operations instructions. Use existing `OrderIntent`, `RunnerSettings`, market normalization and `EventJournal` contracts. Preserve existing runners and adapters' public behavior. Default the new CLI to offline planning; submitting requires an explicit flag and an independently supplied current execution specification. No scheduled job, Gateway login, account selection or order submission is part of implementing this design.

Initial supported allocation is a single US equity/ETF purchased in USD using USD cash and optional SGD-to-USD conversion, with SGD account valuation. This makes the instrument, allocation policy, limits and time window configurable without pretending the recovered arithmetic is multi-currency or multi-market. Other currencies, selling positions, leverage, concurrent account writers and automatic retries remain unsupported. FX commands use explicit currency-pair metadata; they are not equity targets and must not broaden the research handoff schema implicitly.

## Contracts and components

- `packages/execution_policies/paper_allocation.py`: pure Decimal allocation math. An explicit policy carries target gross weight, maximum SGD target, maximum shares, reference price/date, spread limits, stock/FX slippage, cash buffer and qualified tick sizes. No broker or replay imports. Cash, NAV and gross exposure currencies are explicit in the input contract. Quantize limits upward to supplied ticks, shares downward, and account for the existing USD balance before converting SGD. Reject non-finite or negative values, invalid limits, crossed/delayed/stale quotes, insufficient settled cash and exposure at or above target. Use timezone-aware reference/session dates supplied by current qualification, never October constants.
- `apps/execution_runner/paper_allocation.py`: orchestration through a narrow injected broker port and clock. Parse a strict, versioned private specification containing run ID, Paper account, instrument identity, session/window, policy and connection settings. Reuse `OrderIntent` for identity/side/quantity and add a typed limit command carrying stage, contract identity, currency, limit, tick and IOC time-in-force. Keep `BrokerCommand` metadata outside the v1 research target contract. The initial input is a separate private allocation specification, not `targets.json`: allocation must first derive quantities and FX funding before creating existing `OrderIntent` objects. Integrating the order chain means reusing its intent identity, typed broker-command boundary, broker-observed events and journal/projection, with stock/FX stage metadata. It does not mean claiming the allocation specification is a published research handoff or changing v1 targets schemas.
- `adapters/ibkr/paper_allocation.py`: optional IBKR implementation. Verify exactly the configured DU account on the configured Paper endpoint; prefix or port alone is insufficient evidence. Qualify exact stock and FX contracts, obtain session/tick information, account-scoped positions/open orders and fresh live quotes; run bounded what-if validation for both stages. Submit explicit account-scoped IOC limits with deterministic order references and capture broker order IDs, execution IDs, fill quantities and prices through existing event normalization where applicable.
- `competition_tools/run_paper_allocation.py`: offline plan, explicitly enabled submit and read-only reconcile entry points. Private input/results stay outside source and under the selected project storage contract. `STOP` and existing kill-switch policy are checked before each submission. Error exit codes distinguish blocked, partial, unknown and reconciled states.

## Workflow and recovery

Before broker mutation, validate configuration/time and atomically reserve the run under existing `project_storage.guarded_location`; persist and fsync a claim that survives process failure and canonical/legacy root aliases. Never release the durable claim to retry. A second process/run with the same identity cannot submit; a new ID is not an automatic recovery path. Use an account-level cross-process submission lock in addition to run claims, and reject any account-scoped open orders and unexpected positions under an explicit allowed-position list. This serializes this workflow's writers; external account activity still requires supervision and revalidation. Keep a durable account-level unresolved-attempt marker: any ambiguous, partial or unreconciled broker mutation blocks all new run IDs for that account, not only the original run. Only a successful read-only reconciliation with complete broker evidence may clear that marker under the same account lock; missing history cannot clear it.

Persist intent and submission-attempt events before `placeOrder`. Broker observations, not the attempt event, establish acceptance and fills. A projection is rebuilt from the journal with deterministic identifiers; it must represent requested, acknowledged, partially filled, filled, cancelled and unknown outcomes without inferring missing events. Deduplicate by broker execution identity. Never call a timed-out request rejected.

If FX is needed, wait a bounded time for full fill; request cancellation on timeout and wait a bounded time for confirmation. Partial, rejected, disconnected or unknown FX results stop the workflow and require read-only reconciliation. Do not place a stock order after those states. After full FX fill, re-read settled USD cash, gross exposure, stock/FX quotes, account identity, positions, open orders, STOP and time window. Do not enlarge the original stock quantity or price; recompute and reduce if required. Insufficient settled USD blocks, even if the FX trade is reported filled. Repeat final what-if after any quantity change and check freshness immediately before submission.

Stock submission has the same bounded observation/cancellation and uncertainty semantics. Reconciliation verifies account-scoped executions, remaining orders and position deltas; partial fill stays explicit. The reconcile command reads broker state and appends observations only, never submits, resubmits, converts funds or cancels orders. Restart of an already claimed run directs the user to reconciliation and cannot resume submissions.

## Validation and delivery

First reproduce recovered calculation/test behavior using synthetic values; never publish account-specific fixture values as defaults. Add meaningful tests for policy variation and rounding, input rejection, time boundaries, concurrent claims/account locks, storage aliases, preflight/what-if rejection, changed positions/STOP between stages, stale quotes, full/partial/rejected FX and stock outcomes, disconnect before/after submission, duplicate callbacks, crash recovery and reconciliation without new orders. Use a fake IBKR client to verify exact contracts, account, limits, IOC and order references.

Run root unit tests, Ruff, workflow boundary checks and repository-required CI against the current combined target. Preserve recovery-file hashes and disposition in private retention inventory. Do not delete the original recovery directory as part of code integration. Submit a reviewed PR and honor required checks. Repository AGENTS.md additionally requires actual Paper connection, qualification, submission, cancellation, fills, restart recovery and reconciliation checks for execution-chain changes. Keep this implementation PR unmerged and preserve its branch/worktree if those required checks cannot be authorized and completed; standing merge authorization does not waive that gate. Prepare code, fake-broker coverage and a concrete bounded Paper validation procedure first, then obtain any missing execution authorization for that procedure. Only after all required verification passes may the PR merge and this task's branch/worktree be cleaned up. Mocked success is not broker verification; record actual qualification, what-if and lifecycle results individually.

## Builder decisions

The implementer chooses internal dataclass names, error-code spelling, module subdivision and reasonable finite connection/observation timeouts, documenting the values. Do not add an unrelated general portfolio engine or silently relax reference, settled-cash or market-data validation to make a test pass.
