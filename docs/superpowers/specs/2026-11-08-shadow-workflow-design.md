Implement the user's requested five follow-ups as a bounded offline workflow: clarify declaration versus actual implementation; draft prospective policy; capture immutable current-time shadow decisions; compare later paired observations; explain reported NAV movements; keep crypto/MoE research separate. ## Approach and boundaries

Extend competition_review using stdlib and existing strategy_case/seal helpers. Do not merge the unrelated locked Paper execution worktree or train a pretend fundamental Ranker. Alternatives were to activate automatic trading (not authorized and missing model/policy), or add only another audit checklist (insufficient to support prospective records). Chosen implementation is an offline prospective diary plus explicit later-observation contract and an independent reported-component NAV bridge. This is the implementer's choice.

`shadow_cli prepare --case --output` creates a sealed prospective charter draft, a missing-parameter policy skeleton, and bilingual next-work instructions. Derive only observed account/declaration/weights from verified case; benchmark, weights, risk limits, review calendar, review owner and approach remain null. Draft is not a confirmed policy. Document the two unresolved paths: recover declared Ranker evidence or document the actual policy prospectively and resolve declaration changes through the organizer. No invented allocation or past rationale. Research lanes explicitly isolate competition, crypto and MoE; require frozen data/timing/cost/benchmark and multiple forward periods before promotion.

`shadow_cli record --case --output` calls build_case with the current UTC clock, writes full review and recorded_at plus provenance to a fresh sealed bilingual entry. CLI has no backdating flag. Missing evidence produces blocked, not a maintain instruction. Local clock/seal are not trusted timestamps or external authentication; collection availability and supplied lineage remain attributed. Recording is manual only, no scheduler. A historical snapshot recorded now remains historical and marked by report date.

`shadow_cli evaluate --entry --outcome --output` verifies the entry seal and consumes an explicit external outcome JSON. It evaluates only an unblocked complete recorded case, reads target weights via the recorded target path/hash and current weights from the entry, binds outcome to entry decision.json SHA, account alias and currency, requires recorded_at <= interval start < interval end <= available_at <= current time. Outcome schema competition.shadow_outcome.v1 supplies aware start/end/available_at, base-currency total returns by conid, non_stock_return and benchmark_return, and one_way_cost_bps (0..10000). Returns >=-1, finite signed values, full exact union of current/target conids required. Long-only gross<=1. Non-stock residual models a single aggregate sleeve, not real available cash or an FX ledger. Buy-and-hold weight-at-start hypothetical one-interval returns, initial absolute stock-weight turnover cost, paired differences and benchmark excess are arithmetic diagnostics; no execution, multi-period backtest, statistical superiority or cashflow-adjusted broker performance claim. Missing future outcomes means no actual evaluation; synthetic tests alone verify arithmetic. Never use future results to rewrite an earlier entry.

`nav_change` reads the already sealed Flex raw report and exactly one account/base/period-bound ChangeInNAV row. MTM-mode arithmetic only: require explicit startingValue, endingValue, mtm and all displayed component numeric fields; known inactive realized/unrealized mode fields must be zero. Sum known report components independently, show every nonzero field and residual using Decimal tolerance0.02 base units. Unknown nonzero fields, conflicting periods/rows, missing MTM or other model modes cannot reconcile. Preserve raw TWR without guessing units. Cross-check endingValue against recomputed reconciled latest snapshot at identical period-end date. This is a report-field bridge, not independent security-price versus total-FX attribution: MTM may already contain FX, and field semantics/overlap remain visible. No MTMPerformance or cash-transaction rows added again. Receipt provenance and raw hash verified; official eligibility remains unverified.
